# 2026-09-28 — the 0.3.0 archive verifies with no account and no network

`.github/SECURITY.md` gives three ways to check a release archive. The third is for a machine with
no network: fetch Sigstore's trusted root elsewhere, carry it over with the archive and its
bundle, and name it with `--custom-trusted-root`. Until today it had been run only on a machine
that was signed in to GitHub and online. This is that command on the files of the v0.3.0 release,
signed out and offline.

## Set-up

- GitHub CLI 2.97.0 (2026-07-31), Linux.
- Online: `gh release download v0.3.0 -R sayam/thai-docx-skill -p 'thai-docx-0.3.0.*'` and
  `gh attestation trusted-root > trusted_root.jsonl`.
- Offline: a shell with no network (`unshare -rn`), an empty GitHub CLI configuration
  (`GH_CONFIG_DIR` pointing at an empty folder) and no `GH_TOKEN` or `GITHUB_TOKEN`.
  `gh auth status` answered "You are not logged into any GitHub hosts" (exit 1), and
  `curl https://github.com` answered "Could not resolve host" (exit 6).

## Results

| check | command, as SECURITY.md gives it | result |
|---|---|---|
| the archive | `--bundle … --custom-trusted-root trusted_root.jsonl --source-ref refs/tags/v0.3.0` | `✓ Verification succeeded!`, exit 0; digest `sha256:6d886d722b422ca139bc9ced3e4a887749bfa922a5f635c9a716a5a5ac58aea9`; build and signer workflow `.github/workflows/release.yml@refs/tags/v0.3.0` |
| another ref | the same, `--source-ref refs/tags/v0.2.2` | `✗ Policy verification failed`: expected `refs/tags/v0.2.2`, got `refs/tags/v0.3.0`; exit 1 |
| one byte added | the same, on a copy with one byte appended | `✗ Sigstore verification failed`; exit 1 |
| no trusted root | the second command (no `--custom-trusted-root`), offline | "no valid Sigstore verifiers could be initialized"; exit 1 |

The last row is what SECURITY.md says: the bundle alone still needs the network for Sigstore's
trusted root. Named with `--custom-trusted-root`, it needs neither the network nor an account.

## What this does not show

A trusted root fetched on one day checks archives signed while its keys were current. How long a
saved `trusted_root.jsonl` stays usable for a later release was not tested; fetch it again for
each release.
