# 2026-09-18 — an image is whole, or it is refused; and too large is the user's word

The second item of the triage from the three adversarial reviews of 2026-09-18. Two findings about
images, from two reviewers, each re-run here before it was believed.

## A truncated PNG was embedded and the build said it was fine

Codex (GPT-5) handed the builder twenty-four bytes: a PNG signature and an IHDR saying 1×1, and
nothing else — no pixel data, no end. Both implementations embedded it and reported success:

```
$ python3 … build t.md out.docx
{"ok": true, "counts": {"images": 1}, "findings": [], "warnings": []}   rc = 0
$ unzip -l out.docx | grep media
   24  word/media/image1.png
```

`_image_size` read the width and height out of the IHDR and asked nothing more. But a signature and
an IHDR say how big the picture is, not that its pixels arrived. A copy that stopped, a download cut
off, a file truncated by a full disk — all of them have both, and Word draws a blank frame or
nothing at all. The build said `ok: true` over a document with a hole in it.

### What changed

A PNG must end with its `IEND` chunk and a JPEG with its end-of-image marker, or the build refuses
with `error` and exit 2:

```
image stops partway: a PNG ends with its IEND chunk and this one does not
```

Both implementations refuse alike, with the same message and the same exit code. It is a cheap
check — four bytes at the end — and it catches the whole class: what is written last is what a
truncation loses first.

## A photo too big was reported as a defect in the skill

Cursor's Grok 4.6 built a document around a valid image large enough to push the package past the
size the checker allows. Both implementations answered:

```
{"ok": false, "findings": [{"code": "size", "part": "", "message": "package would decompress to …; refused"}]}
rc = 1
```

SKILL.md, line 50, tells the agent what exit 1 means:

> | 1 | `"findings"` | A defect in this skill. Nothing was written. Do not retry; tell the user and quote the finding codes. |

So a user who put a scan or a photograph in a thesis — the ordinary case — was told the skill is
broken and sent to the issue tracker, for something only they can fix. `check` returned 2 for the
same finding, so the two commands disagreed with each other as well.

### What changed

A `size` finding leaves `build` by the other door: `error`, exit 2, the door for input a user can
change.

```
the document does not fit in a .docx — package would decompress to 34618907 bytes; images are what
makes a document this large, so use smaller ones
```

The exit codes now mean what SKILL.md says they mean: 2 is something to fix in the request, 1 is a
defect in the skill. Nothing else about the finding path moves — a defect in the builder's own XML
still exits 1, still writes nothing, and still names its codes.

## Tests, red before the change

- `tests/test_build.py::test_an_image_that_stops_partway_is_refused` — a PNG cut after its IHDR, a
  PNG cut before its IEND, and a JPEG without its end-of-image marker are each refused with
  "stops partway"; the whole file still builds.
- `tests/test_build.py::test_an_image_too_large_to_carry_is_the_users_problem_not_a_defect` — a
  valid PNG padded past the part cap gives `error`, no findings, exit 2, and no file written.

226 tests pass; ruff and ESLint are clean; the bundle was regenerated by `tools/bundle_js.py`.

## What it says about the checks that were already there

R3 of [`docs/assurance-case.md`](../assurance-case.md) says images are read "only PNG or JPEG **by
magic bytes**", and that held: the file was a PNG by its first eight bytes. The requirement was
about where an image may come from and what kind of file it may be, and it never asked whether the
file was complete. The security review of 2026-09-18 tested R3 with a text file named `.png` and a
symlink out of the tree, and both were refused — the right inputs for the requirement as written,
and not this one.

The lesson is narrow and worth keeping: *a magic-byte check answers "what kind of file is this",
never "is this file whole".*
