# 0004 — Thai in .docx is complex script: five causes every output must avoid

- Status: accepted
- Decided: 2026-09-15

## Where it came from

Thai .docx files generated by AI showed a red spelling squiggle under nearly
every Thai word, and spacing and line breaks that were wrong. Copying a
paragraph and pasting it back as unformatted text cured both at once. The
diagnosis that followed, using that paste as the baseline, is recorded in [S2].

## Decision

Every .docx this skill writes satisfies all five, unconditionally, and the
checker reports each by its number:

1. **Compatibility mode 15, declared exactly once.** `word/settings.xml` carries
   `compatSetting compatibilityMode = 15`. Without it Word opens the file in
   Compatibility Mode, whose layout breaks Thai lines only at spaces.
2. **Every run that holds text is marked complex script.** It carries the empty
   element `<w:cs/>` and `<w:lang w:bidi="th-TH"/>`. The attribute `w:cs` on
   `w:rFonts` names a font; it does not mark the run. Thai belongs in the
   `bidi` slot of `w:lang`, not in `val`.
3. **Proofing is never switched off.** No `<w:noProof/>` anywhere. The tool that
   squiggles Thai is the tool that breaks Thai lines. Hiding squiggles, when
   wanted, is the document setting `hideSpellingErrors` (0009).
4. **Contiguous text with the same formatting is one run.** Word does not break
   a Thai word across runs, so a run boundary inside a word shows up as spacing
   and wrapping errors exactly where inline formatting was.
5. **Complex-script properties stand beside their Latin twins** — the `w:cs`
   font with `w:ascii`, `w:szCs` with `w:sz`, `w:bCs` with `w:b`, `w:iCs` with
   `w:i` — in runs, styles, numbering and footnotes alike. Bullets are a real
   character in a Thai-capable font, never the `Symbol` font.

And every part is valid against the WordprocessingML schema [S7], element order
included: a property in the wrong position can be ignored without any error.

Left out on purpose: anything beyond these five. They are the causes found and
confirmed, not a complete theory of Thai in OOXML; a sixth becomes a new record.

## Why

OOXML keeps two property sets for every run, one for Latin text and one for
complex script [S7], and Thai is complex script. Libraries fill the Latin set by
default, so a generator nobody told otherwise writes text that Word handles as
Latin: English dictionary, Latin line breaking. Unformatted paste cures it
because Word rewrites the run with its own defaults, which fill both sets [S2].
That the bold and italic toggles for Thai are `bCs` and `iCs` follows from the
same split; it is confirmed by eye in the release check of 0012, not assumed.

## Expires when

An application in 0012's list shows one of the five symptoms on a file that
passes all five checks — the model is then incomplete — or Word stops keeping
two property sets.
